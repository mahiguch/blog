## この章で学ぶこと

| 観点 | 内容 |
| --- | --- |
| ML | 本書が扱う予測問題の輪郭。「締切前に取れる情報だけで 3 連単を当てる」モデルを、月次で学習し、日次と直前の 2 段階で推論し、回収率と log-loss で評価するという全体像 |
| システム | 2 つのリポジトリ(Python の boatracecsv と TypeScript / Astro の fun-site)と GCP の役割分担。特に「配信レイヤーは自前の推論パイプラインを持たない」という分離 |

## この本について

boatrace-fun.net は、ボートレース(競艇)の当日全レースについて「スタート予想」と「AI による総合評価」を静的ページとして配信するファンサイトです。ページは JST 08:00〜22:59 のあいだ、上流の CSV が更新されるたびに(最短 2 分間隔で)再ビルドされます。

本書は、このサイトを作って運用する過程で得た知見を、開発の実際の順序に沿ってまとめたものです。データを集めるところから始めて、特徴量を設計し、モデルを学習し、評価指標を決め、GCP で定期実行し、静的サイトとして配信し、そして仮説を「予想者」という単位で A/B 実験して退役させるところまでを 1 冊で扱います。

「機械学習の本」でも「インフラの本」でもなく、その両方を 1 つのシステムとして運用するとどうなるか、を書いた本です。学習した係数をどこに置くか、推論結果をどう配るか、失敗をどう検知するか、といった問いは、モデルの精度とは独立に、しかし精度と同じくらい運用の成否を左右します。本書ではそれらを切り離さずに書きます。

## 対象読者と前提

- Python でデータ処理(pandas など)を書いたことがあるエンジニア
- TypeScript と Astro の基礎(コンポーネント、ビルド)を知っている
- 機械学習は未経験でよい。標準化、線形回帰、制約付き最適化、ベイズ収縮、多項ロジスティック回帰、Plackett-Luce といった概念は、必要になった章で実データを使って説明します
- ボートレースの知識は不要。第 1 章で必要なことをすべて説明します
- GCP の利用経験はなくてよい。ただし Docker とシェルスクリプトの基礎は前提とします

本書の主役はモデルの数式ではなく、モデルをシステムに組み込むときの設計判断です。各章では「なぜそうしたか」を実装と一緒に書きますので、Python か TypeScript のどちらかを読めれば追えるように構成しています。

## この本を読み終えると

- 公開されている 1 レース 1 行の CSV から、自分の特徴量と予測モデルを作れる
- 回収率・的中率・log-loss の違いと、どれで判断すべきかを説明できる
- 予測モデルを Cloud Run Jobs で定期実行し、結果を静的サイトとして配信できる
- 仮説を「予想者」という単位で A/B 実験し、統計的に退役させる運用ができる
- 「できないこと」を必要精度の逆算で証明し、撤退ラインと再挑戦条件を数値で残せる

最後の 2 つは、本書の後半(第 9 章、第 10 章、第 18 章、第 19 章)の主題です。2026 年 8 月末の時点で、このシステムには v1 から v10 まで 10 の予想者が投入され、そのうち 8 つが退役しています。退役の大半は control との回収率差が有意に負だったことによるものですが、成績の劣化が理由ではない退役(同じ役割のスロットが重複したため)も 1 件あります。その記録をそのまま読める形にしたのが本書です。

## 全体アーキテクチャ

システムは 3 つの構成要素からなります。順に、データを収集して予測を計算する層、予測を読んでページを生成する層、そしてその 2 つを定期実行して結ぶ GCP の基盤です。

### boatracecsv(Python)

公式サイトから収集したデータを 1 レース 1 行の CSV にし、GitHub Pages(`https://boatracecsv.github.io/data/...`)で配信するリポジトリです。同時に、特徴量と「強さポイント」(5 要素の偏差値を場別の重みで線形結合した AI 総合評価)を計算し、これも CSV として配信します。すべての CSV は 12 桁の `レースコード`(`YYYYMMDDjjrr`。日付 + 場コード + レース番号)を共通キーとして JOIN できます。

計算は Cloud Run Jobs 上の 3 種類のジョブに分かれています。

| ジョブ | 起動 | 役割 |
| --- | --- | --- |
| `monthly-weights` | 毎月 1 日 JST 06:00 | 直近 6 か月で強さポイントの重みを学習し、決まり手モデルやスジ表などの静的テーブルを再生成して commit する(学習) |
| `daily-sync` | 毎日 JST 07:30 | 出走表・近況・モーター成績を収集し、当日全レースの強さポイントを計算して commit + GCS ミラー + Pub/Sub 通知(日次推論) |
| `preview-realtime` | JST 08:00〜22:59 の 2 分毎 | 締切 5 分前の直前情報(展示タイム・進入コース・気象)と結果・払戻金を収集し、直前情報を反映した強さポイントを更新して GCS ミラー + Pub/Sub 通知(直前推論) |

3 つは同じ Docker イメージから `--command` を切り替えて動きます。学習は月次、推論は日次と直前の 2 段階、という分け方が、本書の第 11 章以降で繰り返し出てくる骨格です。

### fun-site(TypeScript / Astro)

CSV を読んで予想ページを生成し、Cloud Storage + Cloud CDN で配信するリポジトリです。pnpm の monorepo で、`shared`(型と予想者レジストリ)、`batch`(Cloud Run Job)、`web`(Astro)の 3 パッケージからなります。

ここで強調したいのは、**fun-site は自前の推論パイプラインを持たない**、という設計です。データソースは boatracecsv の CSV 1 系統だけで、fun-site 側で行うのは次のことに限られます。

- 5 種類の CSV(レース名、出走表、直前情報、強さポイント、結果)を並列で取得する
- 強さポイントから買い目(3 連単フォーメーション)を生成し、確定済みレースは払戻金と突合して的中率・回収率を計算する
- レースごとに 1 つの JSON を作り、Astro の `getStaticPaths()` で静的ページにする
- GCS にデプロイし、Cloud CDN で配信する

学習も、特徴量計算も、強さポイントの算出も fun-site にはありません。この分離には理由があります。

1. **モデルの変更が UI に波及しない**。予想者の追加や退役は、boatracecsv 側で CSV の出力先が増減し、fun-site 側でレジストリの 1 エントリを書き換えるだけで済みます(第 10 章、第 14 章)
2. **配信側は状態を持たない**。当日ぶんの CSV から毎回フルリビルドするので、途中の失敗は次の更新で自然に回復します(第 13 章)
3. **境界が CSV なので検証できる**。fun-site 側で表示する「寄与の内訳」が上流の値と一致するかを、CSV を突き合わせるだけで確かめられます(第 16 章)

2026 年 5 月の設計時には Vertex AI / Gemini に展開予想を生成させる案も検討されましたが採用されず、上流の強さポイントをそのまま AI 総合評価として提示する方針に確定しています。「配信レイヤーに推論を置かない」という決定は、この時点で固まりました。

### GCP

2 つのリポジトリを結ぶのは GCP のマネージドサービスです。boatracecsv 側の `daily-sync` と `preview-realtime` は、commit と同時に CSV を GCS のミラーバケットにアップロードし、Pub/Sub トピックに完了メッセージを publish します。fun-site 側は Eventarc でそのトピックを購読し、Workflows を 1 ステップ挟んで Cloud Run Job(`fun-site-batch`)を起動します。

Workflows を挟むのは技術的な制約のためです。Terraform の google provider 6.x では Eventarc トリガーの宛先に Cloud Run Service しか指定できず、Cloud Run Job を直接起動できません。Workflows が Pub/Sub メッセージを Job の引数に乗せて渡す中継役になります(第 13 章)。

2026 年 5 月までは fun-site は Cloud Scheduler で朝 1 回だけ動く設計でした。`preview-realtime` が 2 分間隔で CSV を更新するようになったのに合わせて、朝バッチを廃止し、このイベント駆動のチェーンに移行しています。

## 本書で扱わないこと

- **オッズ取得の詳細**。締切 5 分前の集計中オッズを収集する仕組みは存在しますが(`data/previews/{od1,od2,od3}`)、本書では収集方法にも、オッズを特徴量にする手法にも立ち入りません。回収率の計算に使うのは確定した払戻金(`results/payouts`)だけです
- **舟券購入の自動化**。本書のシステムは予想を表示するだけで、投票には一切関与しません。本書の回収率は「もし買っていたら」の仮想計算であり、実際の投票を推奨するものでもありません
- **モデルやライブラリの網羅的な比較**。第 20 章で多項ロジスティック回帰と GBM を比べる場面はありますが、それは「なぜ係数 CSV で推論できるモデルを選んだか」を説明するためで、精度ランキングを作ることが目的ではありません
- **公式サイトの HTML 構造の詳細**。パーサーの層構造と設計方針は第 2 章で扱いますが、個々のページのセレクタや変更履歴は扱いません。取得元の仕様は変わりうるので、実装を参照してください
- **Terraform と GCP の網羅的な解説**。第 11 章と第 13 章では、このシステムが使うサービスと、その選択の理由だけを書きます

## 数値の時点について

本書に出てくる回収率・的中率・p 値などの実測値は、特に断りがない限り **2026 年 8 月時点**のものです。値には可能な限り母数 n を添えます。たとえば 2026 年 8 月 9 日の退役判定では、コース予想(`v6_course`)は control と同一レースで突き合わせたペア比較で回収率 -6.91pt(95% CI [-13.1, -0.5]、p=0.0047、n=3,002)でした。この「同一レースでのペア比較」と「n を添える」という書き方自体が、第 9 章で扱う主題です。

モデルの重みは月次で再学習され、予想者の構成も変わるため、読者が同じ計算を行っても値は一致しません。値そのものよりも、「どの指標を、どの母数で、どう比較して判断したか」に注目して読んでください。

## リポジトリと公開データ

本書が参照する 2 つのリポジトリは、どちらも MIT ライセンスで公開されています。

- https://github.com/BoatraceCSV/boatracecsv.github.io (Python。収集・特徴量・モデル・CSV 配信)
- https://github.com/BoatraceCSV/fun-site (TypeScript / Astro。予想ページの生成と配信)

公開 CSV は `https://boatracecsv.github.io/` をルートに、`data/<種別>/YYYY/MM/DD.csv` のパスで取得できます。主なものを挙げます(全一覧は第 2 章と付録)。

| パス | 内容 | 更新 |
| --- | --- | --- |
| `data/programs/title/` | レース名・グレード・締切時刻 | 日次 |
| `data/programs/race_cards/` | 出走表(選手・モーター・全国平均 ST など) | 日次 |
| `data/previews/{tkz,stt,sui,original_exhibition}/` | 直前情報(展示タイム・進入コース・気象・オリジナル展示) | 2 分毎 |
| `data/results/realtime/` | 着順・決まり手・ST | 2 分毎 |
| `data/results/payouts/` | 払戻金 | 2 分毎 |
| `data/estimate/{predictor_id}/` | 予想者ごとの強さポイント(5 要素の偏差値 + 寄与 + 合計) | 日次 + 直前 |

すべてのファイルが `レースコード` を持つので、pandas なら数行で結合できます。

```python:join_example.py
import pandas as pd
BASE = "https://boatracecsv.github.io/data"
day = "2026/08/22"
title   = pd.read_csv(f"{BASE}/programs/title/{day}.csv",   dtype={"レースコード": str})
results = pd.read_csv(f"{BASE}/results/realtime/{day}.csv", dtype={"レースコード": str})
payouts = pd.read_csv(f"{BASE}/results/payouts/{day}.csv",  dtype={"レースコード": str})
df = title.merge(results, on="レースコード").merge(payouts, on="レースコード")
```

`レースコード` を文字列として読むのがポイントです。先頭が `2026...` なので整数でも読めますが、場コードが 1 桁の場合の `0` 埋めや、他ファイルとの型不一致で JOIN が空になる事故を防ぐため、本書では一貫して文字列で扱います。2026 年 8 月 22 日ぶんでは 3 ファイルとも 156 レースで、結合後も 156 行になります。

本書の演習はすべて、この公開 CSV だけで解けるように作ってあります。GCP のアカウントも、公式サイトへのアクセスも必要ありません。

## 演習

1. 上の `join_example.py` を任意の日付で動かし、`title`・`results`・`payouts` の行数が一致するか確かめてください。一致しない日があれば、`title` の `中止状態` 列を見て理由を考えてください。
2. `data/estimate/v1_basic/YYYY/MM/DD.csv` を同じ日付で読んでください。1 レースにつき 2 行あり、`状態` 列が `daily` と `realtime` に分かれています。`realtime` の行だけを `レースコード` で `results/realtime` と結合し、`強さpt` が最も高い枠が 1 着だった割合を、母数 n を添えて記録してください(この値の意味と限界は第 9 章で扱います)。
3. 同じレースの `daily` 行と `realtime` 行を比べ、5 つの成分(枠番pt・選手pt・モーターpt・展示pt・気象pt)のうちどれが変わり、どれが変わらないかを調べてください。なぜそうなるのかは第 3 章と第 4 章で扱います。

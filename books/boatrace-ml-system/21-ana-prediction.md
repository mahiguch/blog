## この章で学ぶこと

| 観点 | 内容 |
| --- | --- |
| ML | 条件付き分布をテーブルにする、Plackett-Luce で順列の確率を作る、確率分布のブレンド、ベイズ収縮が効く場合と効かない場合、A/B の主判定を回収率ではなく log-loss に置く |
| システム | フォーメーションで表せない買い目を上流(boatracecsv)で確定して CSV で配る、`build_index → build_kimarite_probs → build_kimarite_picks` の依存順序、退役判定を月次 CSV で自動化する |

第 20 章では、決まり手 × 1 着コースの 32 クラスを多項ロジスティック回帰で予測する Stage1 と、その確率が校正は良いのに argmax は使えない、という話をしました。この章はその続きで、「確率からどうやって買い目を作るか」を扱います。

穴予想には 2 つの案があります。A案 `v9_suji`(スジ予想)は学習をほとんど要らない簡易版、B案 `v10_kimarite`(穴予想)は Stage1 を土台にした確率モデルです。2 案を 2026 年 8 月に並行運用し、10 日で A案を退役させました。なぜそうなったかを、買い目の作り方、収縮の効き方、判定方法の順に見ていきます。

## 1. A案: スジ表(v9_suji)

### 1.1 買い目の作り方

「スジ」とは、1 着がどのコースかで 2 着・3 着の並びに型があるという競艇の経験則です。3 コースがまくり差せば 1 コースが 2 着に残りやすい、4 コースがまくれば 5 コースがついてくる、という類のものです。A案はこれをそのまま条件付き確率のテーブル(スジ表)にします。

- **1 着** = 1 コース以外で強さpt(第 7 章)が最大の艇。決め打ちで 1 艇
- **2-3 着** = スジ表 `P(2着コース, 3着コース | 1着コース)` の上位 5 ペア
- 各出目に決まり手の注釈(「3 コースの まくり差し」)を添える

スジ表は 1 着コース 6 通り × 残り 5 コースから 2 つ選ぶ順列 20 = 120 行しかありません。`data/results/realtime`(1〜3 着の艇番と決まり手)と `data/previews/stt`(展示進入コース)を突き合わせ、艇番をコースに読み替えて数えるだけです。実際のテーブル(2026 年 9 月時点、`data/estimate/suji/tables/suji_table.csv`)から 1 着 3 コースの行を抜くと次のようになります。

| 1着 | 2着 | 3着 | n | 確率 |
| ---: | ---: | ---: | ---: | ---: |
| 3 | 1 | 4 | 708 | 0.1221 |
| 3 | 1 | 5 | 623 | 0.1074 |
| 3 | 1 | 2 | 618 | 0.1066 |
| 3 | 2 | 4 | 362 | 0.0624 |
| 3 | 1 | 6 | 360 | 0.0621 |

「3 コース頭なら 2 着はほぼ 1 コース」という型がそのまま数字になっています。強さpt で 3 コースの艇を 1 着に選んだレースでは、この上位 5 ペアが買い目です。

生成は `scripts/build_suji_table.py`、買い目は `scripts/build_suji_picks.py` で、どちらも標準ライブラリだけで書いてあります(結果 CSV さえあれば venv 無しで再生成できるようにするためで、`build_course_rate.py` と同じ方針です)。

### 1.2 学習窓と収縮を「回収率で選ばない」

A案で決めるべきパラメータは、学習窓の長さと収縮強度 `k` の 2 つだけです。まず回収率で選ぼうとして失敗した記録が `notebooks/ana_prediction/report.md` に残っています(valid = 2026-06-25〜07-17 の 3,696 レース、test = 2026-07-18〜08-11 の 3,532 レース)。

| 学習窓 | valid 回収率 | test 回収率 |
| --- | ---: | ---: |
| 1 ヶ月 | **77.9%** | 78.3%(最下位) |
| 2 ヶ月 | 77.1% | 83.6% |
| 3 ヶ月 | 71.7% | **84.1%** |
| 4 ヶ月 | 73.2% | 80.0% |
| 6 ヶ月 | 73.2% | 82.9% |
| 全履歴 | 71.3%(最下位) | 80.6% |

valid で最良の 1 ヶ月窓が test では最下位、valid で最下位の全履歴が test では中位です。95%CI は ±12〜14pt あり、全構成が互いの CI に収まっています。回収率で選ぶと valid のノイズに過学習するだけで、第 9 章で見た「回収率で選ぶと何が起きるか」がここでも起きています。

そこで選定指標を、真の 1 着コースを与えたときの `P(2着, 3着 | 1着)` の log-loss に変えました。1 着の選び方(強さpt)から独立に、スジ表そのものの質だけを測る指標です。

| 構成 | valid | test |
| --- | ---: | ---: |
| 一様(20 通り) | 2.9957 | 2.9957 |
| 1 ヶ月 | 2.8257 | 2.8386 |
| 2 ヶ月 | 2.8204 | 2.8311 |
| 3 ヶ月 | 2.8177 | 2.8287 |
| 4 ヶ月 | 2.8146 | 2.8275 |
| 6 ヶ月 | 2.8144 | 2.8275 |
| **全履歴** | **2.8144** | **2.8274** |
| 全履歴 + k=1000 | 2.8144 | 2.8273 |

窓長に対して単調に改善して 4 ヶ月で飽和し、valid と test の順序が完全に一致します。収縮は効きません。`k=50` と `k=200` は `k=0` と小数 4 桁まで同一で、`k=1000` でも 0.0001 nat しか動きませんでした。スジ表は 120 セルしかなく、全履歴なら 1 セルあたり平均 290 レースあるので、収縮が効くほど疎ではないのです(収縮が効く場合との比較は第 4 節)。

スジ表が持つ情報量は一様分布比で 0.18 nat。これがこのテーブルの持つ全てで、飽和しているのなら窓を切る理由が無いので、パラメータを 1 つ減らせる全履歴・収縮なしを本番構成にしました。

### 1.3 場別スジ表は効かない

「イン天国と波乱場でスジは違うのでは」という仮説も検証しました。`build_suji_table.py --by-stadium` で場別セルを全場プール分布へ `k` で収縮した表を作り、同じ条件付き log-loss で比べます。

| 構成 | valid | test |
| --- | ---: | ---: |
| **全場プール** | **2.8144** | **2.8274** |
| 場別 k=0 | 2.9981 | 3.0096 |
| 場別 k=20 | 2.8385 | 2.8490 |
| 場別 k=50 | 2.8299 | 2.8410 |
| 場別 k=150 | 2.8209 | 2.8330 |
| 場別 k=400 | 2.8162 | 2.8288 |

どの `k` でもプールに追いつきません。`k → ∞` で場別はプールに収束するので、これは「場の次元を足しても情報が増えず、ノイズだけ増える」ことを意味します。収縮なしの場別は一様分布より悪く、1 場 1,700 レース ÷ 6 コース ÷ 20 ペア ≒ 14 件/セルでは過学習します。

理由は分解すると明快でした。

| | 戸田 | 平和島 | 福岡 | 徳山 | 大村 | 全場 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 コースの 1 着率 | 42% | 46% | 59% | 62% | 62% | — |
| P(2着=1c \| 1着=3c) | 29.8% | 30.9% | 33.2% | 38.4% | 45.0% | **39.5%** |
| その n | 245 | 178 | 193 | 185 | 151 | 4,382 |

1 着率は場によって 20pt 違うのに、1 着が決まった後の 2-3 着の並びは n=150〜245 の標本誤差(二項の 2SE ≒ ±7pt)にほぼ収まります。**場差は「誰が 1 着になるか」に出て、「1 着が決まった後の並び」には出ない**。3 コースがまくったらインが残りやすい、というターンの物理は場によらないと考えられます。しかも A案の 1 着は強さpt で選んでおり、その `waku` 成分は場 × 季節 × コース勝率、重みも場別に学習されています(第 7 章)。場の情報はすでに 1 着選択側に入っていて、スジ表に重ねて持たせる必要がありません。

`--by-stadium` フラグと CSV の `場コード` 列は残してあります。データが増えて結論が変わったときに、フラグを立てるだけで切り替わるようにするためです。

### 1.4 ホールドアウトの実測

本番構成(全履歴・収縮なし)の test 実測(2026-07-18〜08-11、3,532 レース、上位 5 点を 1 点 100 円)は次のとおりです。

| 指標 | A案 `v9_suji` | control `v1_basic`(同期間、再実装) |
| --- | ---: | ---: |
| 回収率 | **80.6%**(95%CI [68, 94]) | 86.2% |
| 的中率 | 10.25% | 45.6% |
| 平均配当 | **3,931 円** | 2,166 円 |
| 点数 / レース | 5.0 | 11.5 |
| 万舟的中 | 27 本 | 40 本 |
| 万舟 / 1 万円賭け | **0.153** | 0.10 |

回収率は control と同水準で、購入額は 43%、平均配当は 1.8 倍。「当たらないが当たれば大きい」穴予想として成立しています。

一方で実装して初めて分かった性質もあります。A案の 2-3 着はスジ表由来の定数で、レースごとに変わるのは「1 着に誰を選ぶか」だけです。実データ(2026-08-10、156 レース)では買い目のパターンが 1 日で 20 種類しか出ず、上位 4 パターンで 83% を占めました。設計どおりの挙動ですが、ユーザーには「毎回同じ買い目が出る」と見えます。この体験上の差は log-loss や回収率とは別に観察することにしました。

## 2. B案: 決まり手モデル(v10_kimarite)

B案は Stage1 の 32 クラス確率を土台に、120 通りの 3 連単の確率分布を作り、その上位を買います。パイプラインは 5 段です。

1. **Stage1**: 決まり手 × 1 着コースの 32 クラス確率 `P1[セル]`(第 20 章)
2. **Stage2**: セル条件付きの 2-3 着表 `P(2着, 3着 | セル)`(k=150 で収縮)に、強さpt で変調(γ=0.5)
3. **合成**: セルで周辺化して `P(c1, c2, c3)` の 120 通りにする
4. **ブレンド**: Plackett-Luce(強さpt, β=2.4)と w=0.7 で混ぜる
5. **買い目**: 1 コース頭を除いた確率上位 5 点

![Stage1 × Stage2 → 合成 → ブレンド → 上位 5 点のパイプライン](/images/boatrace-ml-system/ana-prediction-pipeline.png)

### 2.1 Stage2: セル条件付きの 2-3 着表

A案のスジ表が 1 着コースだけで条件付けるのに対し、Stage2 は決まり手も込みで条件付けます。同じ「1 着 3 コース」でも、まくりとまくり差しでは 2 着の分布が全く違うからです。設計時の集計(実進入コース基準)では、まくり差し 1 着 3c の 2 着 1c が 63.4% なのに対し、まくり 1 着 3c の 2 着 1c は 22.6% でした。

本番のペア表(`data/estimate/kimarite/tables/pair_table.csv`、2026 年 9 月時点)で同じ 2 セルの上位を並べると、型の違いがそのまま見えます。

| セル | 上位ペア(2着-3着: 確率) |
| --- | --- |
| まくり差し_3 | 1-4: 0.205、1-5: 0.176、1-2: 0.152、1-6: 0.096、2-4: 0.050 |
| まくり_3 | 4-5: 0.075、4-1: 0.066、1-4: 0.064、4-2: 0.064、1-5: 0.063 |

まくり差しなら 2 着 1 コースに集中し、まくりなら外に散る。差し・まくり差しは 2-3 着が絞れて(設計時の集計で top5 が 68%)、まくりは散る(top5 で 35〜42%)という構造です。

この表は 32 セル × 20 ペア = 640 行で、スジ表と同じく周辺分布の積 `m2 ⊗ m3` を事前分布にしたベイズ収縮 `(count + k · m2 ⊗ m3) / (n + k)` で作ります(`scripts/build_kimarite_pairs.py`)。スジ表では収縮が無意味でしたが、こちらは効きます。ホールドアウト(2026-07-18〜、3,792 レース)の条件付き log-loss は `k=0` で 2.8148、`k=50` で 2.8027、**`k=150` で 2.8024**、`k=300` で 2.8025、`k=1500` で 2.8051(一様 2.9957)でした。50〜300 は横ばいで、`k=0` だけ明確に悪い。セルが 32 個に分かれてサンプルが減ったぶん、収縮の出番があるわけです。

同一ホールドアウトで、スジ表の条件付き log-loss 2.8274 に対し Stage2 は 2.8024。決まり手で条件付けたぶん 0.025 nat 鋭くなっています。

### 2.2 3 本の数式

B案の中核は `scripts/boatrace/kimarite_blend.py` にあり、数式は 3 本です。

**Stage2 の変調**。ペア表は「決まり手の型」を表す静的テーブルなので、レースごとの個別化は強さpt で行います。コース c に入る艇の強さpt を `z_c = (強さpt − 50) / 10` と z 得点にして、

```
P(c2, c3 | cell) ∝ tab[cell][c2][c3] · exp(γ · z_c2) · exp(γ · z_c3 / 2)
```

γ が「同じ決まり手なら強い艇が上に来やすい」を表します。3 着の指数は 2 着の半分にしてあります(設計書に理由は明記されていませんが、着順が下がるほど強さの影響が薄い、という仮定だと考えられます)。セルの 1 着コースと同じコース、および `c2 == c3` は 0 にしてセル内で正規化します。

**合成**。1 着コースが c1 になるセルを全部足し合わせ、セルを周辺化します。

```
P(c1, c2, c3) = Σ_{cell: 1着コース = c1} P1[cell] · P(c2, c3 | cell)
```

Stage1 の確率 `P1[cell]` が重みで、セルごとに違う 2-3 着分布を混ぜているのがポイントです。「3 コース頭」の確率は、まくり_3 とまくり差し_3 とその他_3 の確率の和になり、2-3 着の分布はその比率で混ざります。

**ブレンド**。決まり手モデル単体では強さpt を γ 変調でしか使っていないので、強さpt だけで作った順列分布(Plackett-Luce、第 3 節)を混ぜます。

```
P_final = w · P(決まり手モデル) + (1 − w) · P(Plackett-Luce, β)
```

両者は補完的で、混ぜると単独より良くなります。test(2026-07-18〜、3,614 レース)の 3 連単 log-loss は、一様 4.7875、Plackett-Luce 単体(β=1.4)4.0382、決まり手モデル単体 3.9644、**ブレンド 3.9196** でした。

最後にコースを艇番に写像すれば出目です。合成もブレンドも 120 通りをコース番号で持ち、艇番への写像は買い目を作るときだけ行います。前付けで進入が変わっても、分布の計算は変わらないようにするためです。

### 2.3 ハイパラの再選定

設計書 §4.3 に元々書かれていたハイパラは `k=1000 / γ=1.0 / β=1.4 / w=0.8` でした。これは 28 クラス・実験窓(train 6,956 レース)で選んだ値で、32 クラス・全履歴(Stage1 34,222 レース / Stage2 35,016 レース)の本番構成では選ばれません。同じ手続き(valid 3,696 レースの 3 連単 log-loss)で選び直した結果が次の表です。

| | 実験時(28 クラス) | **本番(32 クラス・全履歴)** |
| --- | ---: | ---: |
| k(Stage2 の収縮) | 1000 | **150** |
| γ(強さpt 変調) | 1.0 | **0.5** |
| β(PL の強さ倍率) | 1.4 | **2.4** |
| w(決まり手モデルの重み) | 0.8 | **0.7** |

valid log-loss の感度(他の 3 つを固定して 1 軸ずつ動かす)は、

```
γ  0:3.9193  0.25:3.9097  0.5:3.9065  0.75:3.9095  1:3.9184  1.5:3.9519
β  1.4:3.9188  1.8:3.9091  2:3.9069  2.4:3.9065  2.8:3.9098
w  0:4.2394  0.5:3.9205  0.6:3.9097  0.7:3.9065  0.8:3.9108  1:3.9477
```

で、いずれも内側に最小があり周辺は平坦です(γ 0.25〜0.75 / β 1.8〜2.8 / w 0.6〜0.8 で差 0.005 nat 以内)。`w=0`(β=2.4 の PL 単体)と `w=1`(決まり手モデル単体)のどちらも `w=0.7` より悪い、というのがブレンドの根拠です。

2 点だけ補足が要ります。

**β が 2.4 になる理由**。Plackett-Luce 単体の最良は β=1.4(valid 4.0258 / test 4.0382)で、β=2.4 単体は test 4.2758 と明確に悪い。ところがブレンド成分としては 2.4 が最良です。混合の相手として使うときは、決まり手モデルが持たない「強さの順位」を鋭く主張させたほうが効く、ということだと考えられます。`kimarite_blend.py` では `BETA`(2.4、ブレンド用)と `PL_BASELINE_BETA`(1.4、A/B の対照用)を別の定数にしてあり、混同すると対照が弱くなって B案が有利に見えてしまうので注意が要ります。

**k を 150 に据え置いた理由**。120 通りの log-loss で k を選ぶと単調に大きい方が良くなります(50: 3.9071 → 2000: 3.9037)が、40 倍動かして 0.0034 nat しか変わらず、これはブレンド全体の改善幅 0.12 nat の 3% で実質フラットです。一方 Stage2 側の条件付き log-loss は Stage2 の質そのものを直接測っていて、k=150 に明確な最小があります。測っている対象が鋭い方の選定を採る、という判断です。

本番の合成は標準ライブラリだけ、この検証は numpy 版ですが、同じ入力(2026-08-12 の 180 レース)で 120 通りすべてを突き合わせて最大差 3.3e-16(倍精度の丸め)を確認してあります。報告した数値は本番が実際に計算する分布のものと言えます。

## 3. Plackett-Luce

Plackett-Luce は、各要素に「強さ」を割り当て、それに比例する確率で 1 位を引き、残りから 2 位を引き、さらに残りから 3 位を引く、という順列の生成モデルです。ここでは強さを `exp(β · z_c)` にします。z 得点が 1 高い(強さpt で 10pt 高い)艇は `exp(β)` 倍引かれやすい、という意味で、β が「強さpt の差をどれだけ強く信じるか」を決めます。β=0 なら一様分布(1/120)、β を大きくするほど最強艇の 1 着に確率が集中します。

`kimarite_blend.py` の実装は次の 30 行に尽きます。

```python:pl_blend_min.py
import math

TRIPLES = [
    (a, b, c)
    for a in range(1, 7)
    for b in range(1, 7)
    for c in range(1, 7)
    if a != b and b != c and a != c
]  # 3連単 120 通り。コース番号で持つ


def z_scores(strength_by_boat: list[float], boat_at: list[int]) -> list[float]:
    """コース 1..6 に入る艇の 強さpt → z 得点。boat_at[c] はコース c の艇番。"""
    return [(strength_by_boat[boat_at[c] - 1] - 50.0) / 10.0 for c in range(1, 7)]


def plackett_luce(z: list[float], beta: float = 2.4) -> dict[tuple[int, int, int], float]:
    """z 得点(コース順)→ 120 通りの順列確率。"""
    s = [math.exp(beta * v) for v in z]
    total = sum(s)
    out = {}
    for a, b, c in TRIPLES:
        d2 = total - s[a - 1]   # 1 着を除いた残りの重み
        d3 = d2 - s[b - 1]      # 2 着も除いた残り
        out[(a, b, c)] = s[a - 1] / total * s[b - 1] / d2 * s[c - 1] / d3
    return out
```

`z_scores` が艇番順の強さpt をコース順に並べ替えているのは、120 通りをコース番号で持つためです。前付けで 4 号艇が 2 コースに入れば `boat_at[2] = 4` になり、2 コースの強さは 4 号艇の値になります。

ブレンドと買い目の側も、本質は 30 行です。

```python:pl_blend_min.py
GAMMA, BETA, BLEND_W, TOP_K = 0.5, 2.4, 0.7, 5


def kimarite_joint(p1: dict[str, float], tab, z, gamma=GAMMA):
    """Stage1 のセル確率 × Stage2 のペア表(強さpt で変調)→ 120 通り。"""
    mod2 = [math.exp(gamma * v) for v in z]
    mod3 = [math.exp(gamma * v / 2) for v in z]
    joint = {t: 0.0 for t in TRIPLES}
    for cell, weight in p1.items():
        c1 = int(cell.rsplit("_", 1)[1])          # "まくり差し_3" → 3
        raw = {(c2, c3): p * mod2[c2 - 1] * mod3[c3 - 1]
               for (c2, c3), p in tab[cell].items()}
        s = sum(raw.values())
        for (c2, c3), v in raw.items():
            joint[(c1, c2, c3)] += weight * v / s   # セル内で正規化してから足す
    total = sum(joint.values())
    return {t: v / total for t, v in joint.items()}


def blend(p1, tab, z, gamma=GAMMA, beta=BETA, w=BLEND_W):
    """最終確率 = w · 決まり手モデル + (1−w) · Plackett-Luce。"""
    kim = kimarite_joint(p1, tab, z, gamma)
    pl = plackett_luce(z, beta)
    return {t: w * kim[t] + (1.0 - w) * pl[t] for t in TRIPLES}


def top_picks(probs, top_k=TOP_K, exclude_first_course=1):
    """1 コース頭を除いた確率上位 top_k 点。同確率は出目の昇順で決定的に。"""
    items = [(t, p) for t, p in probs.items() if t[0] != exclude_first_course]
    items.sort(key=lambda kv: (-kv[1], kv[0]))
    return items[:top_k]
```

`top_picks` は除外後に正規化しません。返す確率は 120 通り全体(合計 1)の中での値で、「この出目が来る確率」としてそのまま fun-site の穴予想詳細ページに出ます。同確率の並びを出目の昇順で決定的にしているのは、直前バッチが 2 分毎に再実行されても同じ買い目が出るようにするため(冪等性)です。

合成データで動かしてみます。強さpt を艇番順に `[62, 48, 55, 51, 45, 39]`、進入を 4 号艇の前付け(艇番 → コースが `[1, 3, 4, 2, 5, 6]`)、Stage1 は逃げ_1 を厚くした乱数、ペア表はセルごとに合計 1 の乱数にしました。

```
z (course order): [1.2, 0.1, -0.2, 0.5, -0.5, -1.1]
PL top3: [((1, 4, 2), 0.1026), ((1, 2, 4), 0.0771), ((1, 4, 3), 0.0674)]
picks (course): [((4, 1, 2), 0.0264), ((2, 1, 4), 0.0179), ((4, 1, 3), 0.0143), ...]
picks (boat):   ['3-1-4', '4-1-3', '3-1-2', '4-1-2', '3-1-5']
max |diff| PL = 0.00e+00, blend = 0.00e+00
```

2 コースには 4 号艇(51pt、z=0.5)が入っているので、PL は 1-4-2 ではなく「1 コース - 4 コース - 2 コース」を最上位に置き、買い目は 1 コース頭を除いた上位 5 点になっています。最終行は同じ入力を本番の `kimarite_blend.py` に通した結果との最大差で、簡略版と本番が 120 通りすべてで一致することを確認しています。

## 4. 収縮が効くとき、効かないとき

この本ではベイズ収縮が何度も出てきました(第 5 章のモーター指数、第 18 章の ST 推定)。穴予想では同じ「周辺分布の積(または上位のプール)へ `k` で縮める」式を 3 種類のテーブルに適用して、効き方が 3 通りに分かれました。

| テーブル | セル数 | 1 セルあたりの n | 採用した k | 根拠 |
| --- | ---: | ---: | ---: | --- |
| コースpt(場 × レース番号 × コース、`v6_course`) | 288 行(場 × レース番号) | 約 110〜160 | **50** | log-loss が k=0 の 1.3654 から k=50 で 1.3316 に改善、k=100 の 1.3305 と誤差圏 |
| Stage2 のペア表(セル × 2-3 着) | 32 × 20 = 640 | セルにより大きく違う | **150** | 条件付き log-loss が k=0 の 2.8148 から k=150 で 2.8024 に改善、50〜300 は横ばい |
| スジ表(1 着コース × 2-3 着) | 6 × 20 = 120 | 約 290 | **0** | k=50 / 200 が k=0 と小数 4 桁まで同一 |
| 場別スジ表(場 × 1 着コース × 2-3 着) | 24 × 120 | 約 14 | **∞(= プール)** | どの k でもプールに追いつかない |

判断の軸は「セルあたりの観測数が、そのセルの分布を語るのに足りているか」です。

- コースpt は 1 セル 110〜160 レースで 6 値の分布を語るので、そこそこ足りているが k=0 だと生セル率がノイズを拾う。軽い収縮が最適
- Stage2 は 32 セルに分かれ、セルごとの観測数は `逃げ_1` の 24,047 レースから `その他_5` の 5 レースまで極端に偏る(2026 年 9 月時点の `pair_table.csv` の `n` 列をセルで合計)。20 ペアの分布を数件で語ることはできず、周辺分布の積へ強めに縮める
- スジ表は 120 セルに全履歴を注ぐので 1 セル 290 レース。20 ペアの分布を語るには十分で、縮めても何も変わらない
- 場別スジ表は 1 セル 14 件で過学習し、縮めるとプールに戻るだけ。これは「収縮が足りない」のではなく「場の次元が情報を持っていない」ことの表れ

4 番目のケースが重要です。収縮は「疎なセルをプールで補う」道具であって、「次元を足す根拠」にはなりません。プールに収束していくだけなら、その次元は最初から持たないほうが、パラメータが 1 つ減って運用が軽くなります。第 1.3 節のとおり、場の情報はすでに 1 着選択側にあったので、失うものもありませんでした。

同じ式を使っていても、`k` の値は指標で測って決めるものであり、他のテーブルの値を流用してはいけない、というのが実務上の教訓です。実際、設計時の Stage2 の `k=1000` は 28 クラスの実験構成で選んだ値で、スジ表にそのまま持ち込むと「過大」でしたし、本番の 32 クラスでは 150 に落ち着きました。

## 5. A案 vs B案の判定

### 5.1 回収率では優劣を言えない

ホールドアウト(test 2026-07-18〜、3,614 レース、両案同一レース)の実測です。

| 戦略 | 的中率 | 回収率 | 95%CI | 平均配当 | 万舟 | 万舟 / 1 万円 |
| --- | ---: | ---: | --- | ---: | ---: | ---: |
| A案(スジ予想) | 10.27% | 80.6% | [69, 93] | **3,927 円** | **27** | **0.149** |
| **B案(穴予想)** | 12.65% | **87.1%** | [76, 98] | 3,442 円 | 20 | 0.111 |

B案が回収率と的中率で上、A案が平均配当と万舟率で上。買い目 5 点のうち両案で共通するのは平均 2.62 点(完全一致は 1.2%)で、別物の買い目を出しているのに、回収率の CI はどちらも 22pt 幅あり、この差では優劣を言えません。

第 9 章の検出力の逆算をここに当てると、次のようになります(設計時の n=3,527、141 レース/日)。

| 判定指標 | CI 半幅 | 観測された効果 | 効果を検出するのに必要なレース数 | 所要期間 |
| --- | ---: | ---: | ---: | ---: |
| 回収率 | ±13.3pt | +4.2pt | **34,700** | **約 8.2 ヶ月** |
| 回収率(2pt を検出) | 同上 | 2.0pt | 153,000 | 約 36 ヶ月 |
| **3 連単 log-loss** | **±0.0166 nat** | **+0.0961 nat** | **418** | **約 0.1 ヶ月** |

回収率で A案と B案を比べると、8 ヶ月かけないと差が出ません。既存の退役判定(`v6_course` / `v7_aggregate` / `v8_aionly`)は回収率で -6.9〜-10.6pt という大きな劣化だったので 13〜20 日で検出できましたが、A案 vs B案の +4.2pt はその半分以下で、同じ方法では決着しないのです。

### 5.2 log-loss なら決着している

一方、3 連単 log-loss では Plackett-Luce 単体(β=1.4)の 4.0382 に対してブレンドが 3.9196。改善は **+0.1186 nat [+0.1003, +0.1376]**(n=3,614、レース単位の差の正規近似)で、CI の下限が 0 から遠く離れています。既に効果の数倍の精度があり、「決まり手レイヤーが確率の質を上げているか」という問いには決着がついています。

対照を Plackett-Luce にしているのには理由があります。PL は強さpt だけで作った 3 連単分布で、control(`v1_basic`)と A案(`v9_suji`)が持っている情報と等価です。A案は確率モデルを持たないので log-loss に直接は載せられませんが、「A案が使っている情報」に対する B案の上積みは PL との差で測れる、という構図です。

そこで判定は役割を分けます。

| 指標 | 役割 | 判定 |
| --- | --- | --- |
| **3 連単 log-loss** | **主判定**。決まり手レイヤーが確率の質を上げているか | 数週間で決着。B案が PL を有意に上回らなければ B案を退役 |
| 回収率 | **ガードレール**。破滅的な劣化の検知のみ | control 比で -7pt 級の劣化が出たら退役。A案 vs B案の微差は判定に使わない |
| 万舟 / 1 万円、平均配当 | **体験指標**。穴予想として成立しているか | 目標値を置くが有意差判定はしない(検出力が足りない) |

予想者レジストリ(第 10 章)に log-loss を主判定とするスロットが登場するのはこれが初めてなので、`docs/data/estimate.md` に判定方法の違いを明記しました。

:::message
点数(top-k)も回収率では決められません。B案の test では top3 83.8% / top5 87.1% / top8 80.9% / top12 78.0% ですが、valid では top3 80.5% / top5 76.3% と順位が逆になります(どちらも CI ±10pt 級)。top5 は「A案と同じ 5 点・同じ 500 円でペア比較できる」という事前に決めたルールで固定したもので、valid の最良ではありません。
:::

### 5.3 オッズを重ねると悪化する

「確率が上位で、かつ配当が大きい出目だけ買えば良いのでは」という案も試しました。集計中オッズ `od3` が取れる 3,352 レースでのフィルタです。

| 戦略 | 回収率 | 平均配当 |
| --- | ---: | ---: |
| 1 着≠1 の top5(オッズ不使用) | **85.5%** | 3,462 円 |
| 1 着≠1 の top5 × 30〜100 倍 | 76.3% | 4,762 円 |
| 1 着≠1 の top5 × 20〜200 倍 | 82.1% | 4,299 円 |

オッズ帯で絞ると、モデルが上位に置いた出目を捨てて下位を買うことになるため悪化します。`v10_kimarite` はオッズを使いません。オッズを主役にする案(EV = 確率 × オッズの上位を買う)は 30〜100 倍帯で 87.4% を出しましたが、生成原理が「市場との乖離」で人間に説明しづらいため今回は採らず、`od3` の履歴が貯まったら別スロットで再検討することにしています。

### 5.4 本番 10 日での退役

2 スロット運用は 2026-08-12(A案)/ 08-13(B案)に始まり、08-22 に A案を退役させました。本番の realtime 買い目(2026-08-13〜08-22、両案同一の 1,511 レース)の実測です。

| | A案 `v9_suji` | B案 `v10_kimarite` |
| --- | ---: | ---: |
| 的中率 | 8.95% | 11.33% |
| 回収率 | 70.7% | 68.8% |
| 平均配当 | **3,949 円** | 3,035 円 |
| 万舟 / 1 万円 | **0.133** | 0.066 |

買い目の重なりは平均 2.70 点 / 5 点(完全一致 1.3%)で、設計時のバックテスト(2.62 点)と同水準。買い目そのものは半分しか重ならないのに、回収率では区別できない。理由は成績の劣化ではなく、穴予想のスロットを 2 つ並べても差が示せないことでした。確率モデルを持ち主判定の log-loss に載る B案を残し、A案を退役させています。

ただし体験指標(平均配当・万舟率)では A案が上回っています。「穴らしさ」を優先するなら判断は逆になりえます。この点は `registry.py` 冒頭のコメントに記録として残し、再挑戦するなら退役した ID を再利用せず新しい ID を立てる、という既存の規約に従います。

退役後も A案のコードは消していません。B案の `build_kimarite_picks.py` が、決まり手注釈テーブル(`build_suji_table.py` が生成)と `build_suji_picks.py` のヘルパーに依存しているからです。止めたのは日次の買い目生成だけで、スジ表の月次再生成は続いています。

### 5.5 退役判定を月次 CSV にする

B案の主判定は `scripts/build_kimarite_logloss.py` が月次で集計し、`data/estimate/kimarite/tables/logloss.csv` に出します。

| 列 | 説明 |
| --- | --- |
| `集計月` | `2026-08` 等。最終行に `累計` |
| `n` | 対象レース数(状態=realtime かつ確定したレース) |
| `PL_logloss` | 対照 = 強さpt だけで作った分布(β=1.4) |
| `ブレンド_logloss` | B案の分布 |
| `改善nat` | `PL − ブレンド`。正なら B案の勝ち |
| `95%CI下限` / `95%CI上限` | レース単位の差の標準誤差による正規近似 |

**`95%CI下限` が 0 を下回ったら退役**。回収率では判定しません。買い目(`top_picks`)と log-loss 集計が同じ分布を見るように、合成は `kimarite_blend.py` に集約してあり、集計側は `blend()` と `plackett_luce(z, PL_BASELINE_BETA)` を呼ぶだけです。

2026 年 9 月時点のリポジトリにある最初の行は、2026-08 が n=2,639、PL 4.0481、ブレンド 3.9170、改善 +0.1311 [+0.1091, +0.1530] で、ホールドアウトの +0.1186 と同水準を保っています。

:::message alert
この CSV のリポジトリ初出は 2026-09-01 の monthly-weights 実行です。それ以前は sparse-checkout と `git add` の両方から漏れていて、毎月生成されては黙って捨てられていました(2026-08-22 修正)。判定の自動化は「ファイルが永続化されている」ことが前提で、そこが崩れると判定自体が無かったことになります。第 12 章で扱った失敗の型です。
:::

## 6. 買い目を上流で確定する

他の予想者では、fun-site が強さpt からフォーメーション(各着の候補窓の直積、第 8 章)を計算します。穴予想の 2 案だけはそうしません。A案の「上位 5 ペア」も B案の「確率上位 5 点」も、`3-1-5, 3-4-5, 3-5-2` のようにどんな窓でも作れない出目集合だからです。最小フォーメーションで近似すると実際に買う点数が 5 点より増えて回収率が変わり、ホールドアウトの数字が再現しません。

そこで買い目は boatracecsv 側で確定させ、CSV で配ります。

| CSV | 予想者 | 生成 |
| --- | --- | --- |
| `data/estimate/suji/YYYY/MM/DD.csv` | `v9_suji`(2026-08-22 で生成停止) | `build_suji_picks.py` |
| `data/estimate/kimarite/picks/YYYY/MM/DD.csv` | `v10_kimarite` | `build_kimarite_picks.py` |

スキーマは共通で、レース × 状態(`daily` / `realtime`)で 1 行、`買い目1`〜`買い目5`(`3-1-4` 形式の艇番)と `決まり手1`〜`決まり手5`(両案共通の静的テーブル由来の注釈)を持ちます。A案には `1着コース` / `1着艇番` 列がありますが、B案は 5 点に複数の 1 着艇が混ざるのでその列はありません。fun-site は `parseAnaPicks` の 1 つのパーサで両方を読み、`BettingPicks` を `kind: "formation"` と `kind: "combos"` の直和型にして、的中判定と払戻計算を `kind` で分岐させています。バッチと web が必ず同じヘルパー経由で解決する規約(第 8 章、第 13 章)はそのまま維持されます。

B案の CSV には 2026-09-19 に `確率1`〜`確率5` 列を足しました。各出目のブレンド後の確率(120 通りの分布の値そのもの)で、fun-site の穴予想詳細ページが「なぜこの 5 点か」を出すためのものです。fun-site 側で合成を再計算させないのは、表示と集計の分布が食い違う余地を残さないためです。同じ日に `pair_table.csv` と `kimarite_table.csv` も GCS ミラーの対象にして、Stage2 の中身と出目ごとの決まり手分布をページから引けるようにしています。

依存順序は次のとおりで、これを崩すと買い目が 0 行になります。

```
build_index.py --predictor v10_kimarite   … 強さpt
build_kimarite_probs.py                   … Stage1 の 32 クラス確率
        ↓
build_kimarite_picks.py                   … 合成 → ブレンド → 上位 5 点
```

Stage1 の確率が無いレースは買い目を出さずにスキップし、index が無い場合は作り方を示して落ちます(第 12 章)。sparse-checkout では買い目を `data/estimate/kimarite/picks/${TODAY_YM}` という独立したパスで足しています。日次 CSV と静的テーブルを同じ階層に置くと、cone-mode が日次ファイルの全履歴まで checkout してしまうためで、`tables/` サブディレクトリに分けたのも同じ理由です。

## 演習

強さpt から Plackett-Luce で 120 通りの確率を出し、1 か月分の 3 連単 log-loss を β=1.0 / 1.4 / 2.4 で比べてください。必要な公開 CSV は 3 種類です(`https://boatracecsv.github.io/data/` 配下)。

- `results/realtime/YYYY/MM/DD.csv` — `1着_艇番` 〜 `3着_艇番`
- `previews/stt/YYYY/MM/DD.csv` — `艇N_コース`(展示進入)
- `estimate/v1_basic/YYYY/MM/DD.csv` — `N枠_強さpt`(`状態=realtime` の行)

第 3 節の `plackett_luce` と `z_scores` をそのまま使えます。

```python:exercise_pl_beta.py
import csv, math
from pathlib import Path
from pl_blend_min import plackett_luce, z_scores

DATA_DIR = Path("data")  # 公開 CSV を同じパス構造で保存しておく
BETAS = [0.0, 0.5, 1.0, 1.4, 1.8, 2.4, 3.0]


def read_by_race(path):
    if not path.exists():
        return {}
    with open(path, newline="", encoding="utf-8") as fh:
        return {r["レースコード"]: r for r in csv.DictReader(fh)}


def entry_courses(stt_row):
    """艇番 → コース。stt が無い艇は枠なり。重複したら全艇枠なり。"""
    courses = list(range(1, 7))
    if stt_row:
        for b in range(1, 7):
            try:
                c = int(float(stt_row.get(f"艇{b}_コース") or ""))
            except ValueError:
                continue
            if 1 <= c <= 6:
                courses[b - 1] = c
    return courses if len(set(courses)) == 6 else list(range(1, 7))


losses = {b: [] for b in BETAS}
for day in range(1, 32):
    rel = Path("2026") / "08" / f"{day:02d}.csv"
    results = read_by_race(DATA_DIR / "results" / "realtime" / rel)
    stt = read_by_race(DATA_DIR / "previews" / "stt" / rel)
    index = {c: r for c, r in read_by_race(DATA_DIR / "estimate" / "v1_basic" / rel).items()
             if r.get("状態") == "realtime"}
    for code, res in results.items():
        idx = index.get(code)
        if idx is None:
            continue
        try:
            boats = [int(float(res[f"{p}着_艇番"])) for p in (1, 2, 3)]
            strength = [float(idx[f"{b}枠_強さpt"]) for b in range(1, 7)]
        except (KeyError, ValueError):
            continue
        if len(set(boats)) != 3:
            continue
        courses = entry_courses(stt.get(code))
        boat_at = [0] * 7
        for boat, c in enumerate(courses, start=1):
            boat_at[c] = boat
        truth = tuple(courses[b - 1] for b in boats)   # 1〜3 着をコースで
        z = z_scores(strength, boat_at)
        for beta in BETAS:
            losses[beta].append(-math.log(max(plackett_luce(z, beta)[truth], 1e-12)))

n = len(losses[BETAS[0]])
print(f"n = {n}  uniform = {math.log(120):.4f}")
for beta in BETAS:
    print(f"beta = {beta}: log-loss = {sum(losses[beta]) / n:.4f}")
```

2026 年 8 月(状態=realtime、n=4,449 レース)で実行した結果です。

| β | 3 連単 log-loss |
| ---: | ---: |
| 0.0(一様) | 4.7875 |
| 0.5 | 4.3472 |
| 1.0 | 4.1036 |
| **1.4** | **4.0385** |
| 1.8 | 4.0719 |
| 2.4 | 4.2668 |
| 3.0 | 4.5876 |

PL 単体では β=1.4 が最良で、ホールドアウト(2026-07-18〜、3,614 レース)の 4.0382 とほぼ同じ値になります。β=2.4 は単体だと 4.2668 と明確に悪く、これも報告書の 4.2758 と整合します。「単体で最良の β」と「ブレンド成分として最良の β」が違う、という第 2.3 節の話を、対照側の数字で確かめたことになります。

発展として、`logloss.csv` の `PL_logloss`(2026-08 で 4.0481)とこの値を比べてみてください。母数の定義(`v10_kimarite` の index を使う、`started_at` 以降のみ)が違うので一致はしませんが、同じ月の同じ対照がどの程度ずれるかは、判定の頑健さを考える材料になります。
